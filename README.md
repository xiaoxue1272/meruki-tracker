# meruki-tracker

[![CI](actions/workflows/ci.yml/badge.svg)](actions/workflows/ci.yml)
[![Build](actions/workflows/build.yml/badge.svg)](actions/workflows/build.yml)

挖煤姬（meruki.cn）拍卖监视器。命令名 **`meruki-tracker`**（简写 `mt`）。

当前版本 **v1.0.0-SNAPSHOT**。`meruki-tracker --version` / `mt --version` 可查看。
（包元数据为 PEP 440 合法的 `1.0.0.dev0`；对外统一显示为 `v1.0.0-SNAPSHOT`。推 `v*` tag 会自动构建三平台可执行程序并发布到 Release。）

> **它只展示已确认的时间，绝不假装确定。**

---

## 这解决什么问题

旧项目（meruki-auction-monitor）用列表里"2天3小时"这类文本估算结束时间，当成确定值排提醒——然后在错误的时间做事，而你看不出来。

已确认的事实：**详情接口里有精确到秒的结束时间**。

所以本项目的时间模型只有两态：

| 状态 | 含义 | 界面 |
|---|---|---|
| **已确认** | 从详情拿到精确到秒的时间 | 显示倒计时 |
| **待确认** | 还没拉到详情 | 显示"时间待确认"，**不显示倒计时** |

## 快速开始

```bash
uv venv --python 3.12
uv pip install -e ".[dev]"

meruki-tracker        # 直接进入 TUI；首次运行会引导登录
```

**没有配置文件**：所有可调项都在 TUI 里按 `s` 改，存在 `data/meruki.db` 的
`settings` 表里。想恢复默认值，删掉对应那项即可，下次启动会补回默认值。

### 界面结构：列表 + 配置

**没有外层大分页**。程序默认就是列表页，它自己用 `Tab` / `Shift+Tab`
（或 `←` / `→`）切四个视图（**关注中 / 已结束 / 无法确认 / 全部**）；按 `s` 进配置页，
配置页内部同样用 `Tab` / `←` / `→` 切分组
（基本 / 刷新与采集 / 详情与提醒 / 网络 / 存储 / 通知 / 登录）。
**通知的配置全部收在「配置 → 通知」这一组里**——渠道开关、扫码、地址凭据、
发送测试消息都在这里，不用再去别的页配另一半。

右侧那条窄栏是通知摘要，**常驻**在列表页右侧（终端窄于 80 列时自动隐藏），
不占页签也能看见最近要发什么。

### TUI 按键

列表页：

| 按键 | 作用 |
|---|---|
| `↑` `↓` | 选择拍品 |
| `n` / `p` | 翻页（只有一页时页脚不显示这一项） |
| `Tab` / `Shift+Tab` | 切列表视图：关注中 → 已结束 → 无法确认 → 全部（`←` `→` 是同一件事的顺手版本） |
| `Enter` | 查看详情（整屏，`r` 只刷新这一条，`Esc` 返回） |
| `r` | 刷新数据（列表保持可见可操作，进度显示在状态行）。不管当前在哪个视图，拉的都是**「进行中」这一桶 + 关注中的详情**（定时的节奏也一样） |
| `x` | 清理（**仅**在「已结束」「无法确认」视图可用，删本地记录，不取消关注） |
| `s` | **进配置页**（唯一入口；登录 / 换号也在里面） |
| `q` | 在列表上退出程序 |

配置页用 `Tab`（或 `←` / `→`）切分组、`↑` `↓` 选项、`Enter` 修改、
`Esc` / `q` 退回列表；登录 / 详情 / 清理确认 / 挂载这些子屏也是 `Esc` / `q`
退回。`Tab` 只在**编辑态**改回切数值单位（秒 / 分钟 / 小时 / 天）——那条绑定
最后注册，所以编辑时不会误切成下一组。

**扫码没有列表快捷键**：它是「配置 → 通知」组里的动作项，和「登录挖煤姬」
「发送测试消息」摆在一起。而且**每个渠道各一行**（`扫描微信机器人二维码` /
`扫描 QQ 机器人二维码`），各自紧贴自己那一组的凭据——**渠道开关打开后那一行才出现**，
因为扫码换的正是你还没填的那个凭据，渠道关着时摆一行只会让人以为点了就能用。
行本身会显示状态（`已挂载 888888888` / `Enter 打开二维码`），列表页没有入口，
两处都有反而让人分不清哪个才是正经入口。

配置页里有四行**动作项**（不是参数，按 `Enter` 直接执行）：

| 位置 | 动作 | 说明 |
|---|---|---|
| 配置 → 登录 | `登录挖煤姬` | 显示当前状态（`已登录 · Enter 更换` / `未登录 · Enter 登录`），按 `Enter` 进「选择登录方式」屏。**这是唯一的登录入口**：列表页不再有 `l`，页脚也不占那一格 |
| 配置 → 通知 | `扫描微信机器人二维码` | 只在**微信机器人**开关打开后出现，位置紧贴「微信登录凭据」。按 `Enter` 在终端里出二维码，手机微信扫一下就换回凭据。**已经有凭据时只显示「已挂载」**，要换账号才按 `r` 重新取码 |
| 配置 → 通知 | `扫描 QQ 机器人二维码` | 只在**QQ 机器人**开关打开后出现，紧贴「QQ 机器人 AppSecret」。按 `Enter` 出码，手机 QQ 扫码选一个机器人，AppID / AppSecret 自动填回来。手填过的不必再扫 |
| 配置 → 通知 | `发送测试消息` | 给**已启用**的渠道各发一条测试通知，逐条报告成败；没配好的渠道会说缺什么 |

「发送测试消息」也在「配置 → 通知」组里，按 `Enter` 执行；没有独立的通知页。

其它屏幕统一 `Esc` 返回上一屏、`Ctrl+C` 随时退出。页脚会常驻显示当前屏幕
可用的按键——**窄终端下自动降级，但 `q 退出` 永远保留**；列表页还会保住
`s 设置`（它是进配置页的唯一入口）。

详情页：

| 按键 | 作用 |
|---|---|
| `r` | 刷新**这一条**（不退回列表，只重拉当前拍品的详情） |
| `v` | 看商品描述全文（可滚动，`Esc` / `q` 返回详情） |
| `t` | 翻译开关（**全局**，列表页也按 `t`；再按一次切回原文） |
| `Esc` / `q` | 返回列表 |

详情页会显示**商品描述**（前 3 行，超过会提示「按 `v` 看全文」）。描述不在
`auctions` 表里，而是跟着详情原始 JSON 存在 `detail_items.raw_json`，所以每次
拉详情都会顺带更新。

**不显示图片**：挖煤姬的图片地址需要登录认证才能访问，终端里也放不了图
（复制出去打开只会得到 403），所以详情页只给描述，不给图片地址。

**翻译是服务端做的**（`Sig.Front.User.Translate.TranslateHtml`，不需要登录）。
它是个**全局开关**：列表和详情一起生效，`t`（列表页、详情页都一样）或设置里
的「翻译标题与描述」开关都能切。

- 打开后列表直接显示中文标题、详情显示中文标题与描述；开着进出详情、刷新详情
  都会顺带把这一条翻掉，不用手动按。
- 译文落库（`translations` 表），**一个拍品只翻一次**：列表十几条如果每次启动都
  重翻就是十几倍的请求量。之后按 `t` 关掉只是切回原文，译文还在，再开不用重翻。
- 刷新详情时会**重翻一次**——卖家改标题是常事，缓存的旧译文不该一直用。
- 译文是缓存，不是数据：删掉 `translations` 表内容只会让它下次重翻。

### 视图与清理

列表分四个视图，顶部栏常驻显示各自数量：

| 视图 | 含义 |
|---|---|
| 关注中 | 还在进行中、你仍在关注的 |
| 已结束 | 已经不在进行中的（拍完了，或你取消了关注） |
| 无法确认 | 详情连续拉不到、还在**永久重试**的 |
| 全部 | 以上全部 |

**「无法确认」是干嘛的**：详情连续失败若干次后，程序不会放弃——它继续每轮
重试，详情一旦通了自己就恢复成「关注中」。但这些拍品混在「关注中」里会把
正常条目淹掉，也不该被当成"拍完了"藏进「已结束」，所以单独一档。想手动放弃
就在这一档按 `x` 清理；确认屏会说明**这不是永久删除**：如果拍品还在挖煤姬的
关注列表里，下一轮刷新会重新发现它、从零开始重试。清理只清掉当前的失败记录。
这一档**不发结束提醒**——时间没确认上，宁可不说，也不给你一个可能是错的倒计时。

**为什么没有「已取关」视图**：详情接口的 `hasCollect` 能分辨"拍完了"和"你取消
关注了"（见下节），数据里也确实记着 `UNFOLLOWED` 这个状态。但两种情况的结论对
你来说一样——这个拍品都不用再盯了——所以不值得为它单开一栏、再记一堆"能清理、
不能刷新"的规矩。它归到「已结束」视图，剩余列显示「已离开」、行标记 `·`，
照样能按结束时间排序、能清理；以后重新关注还会自动回到「关注中」。

**列表和详情里的剩余时间精确到秒**，用中文单位（`3天 05时07分33秒`、`1时59分59秒`），
并且按紧急程度变色（一小时以内黄色、十分钟以内红色加粗），已结束的压暗。每秒重绘，
不是静态文本。

「已结束」是**关注的流水账**，不是挖煤姬的全站历史：拍品从「进行中」结束（或你
取消关注）之后自然滚进来，一条都不会丢。**不会**去翻那 50 多页历史来同步——
那条链路早删了。所以首次运行时这一档是空的，用得越久越全。
`r` 在任何视图都是同一套刷新（拉「进行中」那一桶 + 关注中的详情），不会去补历史。

**结束后重新开拍也能认出来**：同一件拍品重新上架时，它会重新出现在「进行中」
列表里，系统每轮刷新都会比对，发现"上轮已结束、这轮在进行中"就改回进行中，
并清掉旧的结束时间（否则会算出负的倒计时）。

「已结束」和「无法确认」会一直累积，都可以按 `x` 清理本地记录；确认屏会逐条
列出要删的拍品，并明确说明**只删本地记录，不会取消挖煤姬上的关注**。观测历史
会保留，以后重新关注还能看到过去的记录（「无法确认」的清理还会额外说明它不是
永久删除，见上）。「关注中」和「全部」不提供清理——前者还在跑，后者混着活数据。

整个 TUI 是一个**常驻的全屏应用**：切屏时整屏重绘，不会把面板追加到终端，也不会出现按键回显泄漏。

### 数据是怎么来的

**本地不维护一套自己的状态，只做接口的镜像**：接口返回什么字段就存什么，
下一轮再拉一次、和上一轮比对，差异记成变更事件。

| 表 | 存什么 |
|---|---|
| `list_items` | 关注列表的**全部**字段（`Asin`/`Id`/`Name`/`Url`/`DetailUrl`/`BidDeadline`/`BidDeadlineStr`/`CreatedTime`/`ImageUrl`/`UserId`），外加原始 JSON 兜底 |
| `list_pages` | 分页元信息（`ItemPerPage`/`ShowPageNum`/`TotalItem`/`TotalPage`/本页实际条数） |
| `detail_items` | 详情接口全字段（成交价、一口价、自动延长、提前终止…）+ 原始 JSON |
| `changes` | 逐轮比对的差异事件：新出现 / 消失 / 字段变化 / 详情刷新 |

`auctions` 表是这些数据的**派生投影**（TUI 要看的那个视图），不再是独立事实来源。

### 「结束」是怎么判的

**只看详情**。关注列表接口只返回「进行中」，拍品一结束就自然从列表里消失，
但"消失"既可能是拍完了、也可能是你取消了关注——列表回答不了这个问题。
所以判定只有一条路：每轮刷新把关注中的每一条拍品详情都拉一遍，详情里的
`over` 字段说结束了就是结束了。

> 以前是三条路混着用：按结束时间本地推断、去「已结束」列表翻页查证、详情兜底。
> 用户 2026-11-15 定调：「每条挨个去请求详情，从详情判断是否结束」——推断和查证
> 都删了，`fetch.list_max_pages` / `fetch.ended_probe_pages` /
> `detail.recheck_before_end_minutes` / `detail.max_recheck_per_cycle` 这四个设置项
> 也一起没了。关注列表**翻到底为止**，不再有页数上限。
>
> 「已结束」不再单独同步历史：它的内容由拍品从「进行中」滚过去自然补齐。
> 四个视图（关注中 / 已结束 / 无法确认 / 全部）按 `r` 都是同一套刷新逻辑。
>
> 「已结束」里会显示**结束时间和成交价**。结束时间来自列表接口；成交价只能一条条
> 查详情（列表不带价），所以历史里那一列默认是 `—`。列表按结束时间倒序，最新的在
> 最上面。
>
> **当前价和一口价是两列**。ヤフオク 的「即決価格」商品没有拍卖价（那是"直接买走"
> 的价格），所以列表里看到的是：
>
> | 情况 | 当前价 | 一口价 |
> |---|---|---|
> | 普通拍卖，还没人出价 / 已经有人出价 | `¥1,300` | `—` 或 `¥3,000` |
> | 一口价商品 | `—` | `¥1,980` |
> | 既没出价也没一口价 | `—` | `—` |
>
> 一口价只在**宽终端**（≥ 96 列）有独立一列，窄屏先砍它——当前价是主信息。
>
> **价格从哪来**：列表接口不带价格，只能一条条查详情。
>
> - **每轮刷新都全拉**：关注中的每一条拍品都拉一次详情——价格、结束时间、
>   是否结束全都来自这里。手动按 `r` 和后台定时刷新**没有区别**。
> - **已结束的拍品**：价格不会再变，也不再拉，省请求。
> - **进详情页按 `r`**：只刷这一条，是同一个代码路径。

### 「取关」是怎么判的（不用猜，详情直接说）

详情顶层有个 `hasCollect`（我此刻是否还关注这件商品）。它会明确回答上面那个
"消失 = 拍完了还是取关了"的问题：

| 你看到的 | `hasCollect` | 判定 |
|---|---|---|
| 还在关注列表里 | `True` | 继续关注，每轮照常拉详情 |
| 在网站上取消了关注 | `False` | 标成「已离开」，**从此不再拉详情** |

这个信号和"拍卖是否结束"**完全正交**：2026-11-15 实测，一条用户刚取消关注的
拍品 `hasCollect=False` 但 `over=False`（雅虎又上架了、拍卖还在进行）；而 21 条
早已结束但仍在关注的拍品全是 `True`。所以 `over` 管"拍没拍完"，`hasCollect`
管"我还关不关注"，两个维度各管各的。

> **为什么必须用它**：拍品从「进行中」列表消失后，若没有这个字段，本地既不能
> 判结束（已交给 `over`）也不能判取关，只能一轮轮把详情拉下去、永远问不出答案。
> 有了 `hasCollect=False`，一次请求就能收尾：状态写成 `UNFOLLOWED`，
> `_needs_detail` 的 `user_query is FOLLOWING` 自然不再命中，轮询立刻停。
>
> **不会误杀**：响应里**缺**这个字段（老接口 / 异常响应）时保持原状态不动，
> 只有明确拿到 `False` 才算取关。`collectInfo` 不能当判据——从没关注过的拍品上
> 它也是非空 dict，拿它判断会永远得到"还在关注"。
>
> 取关的拍品**保留本地记录**（不删行），归到「已结束」视图、剩余列显示「已离开」、
> 行标记 `·`，可在该视图按 `x` 清理。以后重新关注时，它重新出现在「进行中」
> 列表里，历史和价格曲线都还在。

### 「出价被超过」：三条信号，只报"被超过"，不猜"还领先"

挖煤姬会主动给你写站内消息：**你出过价的拍品被别人超过时**，它记一条
「您的拍卖 XXXX 价格被超过」。这是服务端**已经替我们判断好**的事实。

但只靠它不够：实测有订单最终成交价高于我的出价、log 里却只有「价格不足」，
**没有任何「出价被超过」的消息**——消息会漏发。所以现在三条信号取或：

| 信号 | 来源 | 覆盖范围 | 会不会漏 |
|---|---|---|---|
| 站内消息 | `GetMessageWeb` 的「价格被超过」 | 你出过价的拍品 | **会**（实测漏过） |
| 价格比对 | 本轮详情的当前价 vs 我的出价 | 你在关注、且本轮拉了详情的拍品 | 不漏 |
| 订单状态 | 「我的竞拍」的 `StatusStr` 写着「价格被超过」 | 所有出过价的拍品（**含没关注的**） | 不漏 |

三条都由服务端或本轮真实数据决定，代价是每轮多一次「我的竞拍」列表请求
（一次请求覆盖所有进行中的出价，不是按拍品逐个查）。

**价格比对的方向是单向的**，这点很关键：

- `当前价 > 我的出价` → **一定**被超过（拿 8 条历史输掉的订单验证，6 条符合，
  没有例外）；
- `当前价 <= 我的出价` → **什么都不能说明**。那 8 条里有 2 条输了但最终价低于
  我的出价（4100 vs 我 5000、920 vs 我 1000），可能是一口价被买走、出价被判
  「价格不足」、卖家取消。所以系统**只报警，绝不反过来说"你还领先"**。

被超过时状态行闪一条、侧栏照常，消息正文会带上当前价：

```
▲ 出价被超过  ■ テスト品 ■ カメラ Camera 690 …（当前 ¥9,380 / 我的出价 ¥6,000）
```

同一条拍品、同一个出价只响一次；你加了价又被超过，会再响一次。

> **已知边界**：价格比对只覆盖你在关注的拍品（没关注的拍品本轮不会拉详情）。
> 但那种情况由「订单状态」兜底——只要你出过价，`StatusStr` 就会写「价格被超过」。
>
> 消息里只有订单号，没有价格。系统靠订单详情把订单号翻译成拍品号
> （订单详情的 `url` 是 hex 编码的雅虎地址），这一步要额外一个请求，所以
> 同一条消息只会处理一次（记住读到哪了，不重复回查）。
>
> 顺带会把该订单的**整条出价记录**存下来（什么时候出价成功、什么时候被超过、
> 最后成没成），比自己只记一个"被超过了"有用得多。
>
> 开关在设置里：`messages.enable`（站内消息）、`notify.outbid_by_price`
> （价格 + 订单状态那条）。两个都关就完全不提醒出价。

### 详情屏上那两行：提前结束 / 自动延长

这两个是拍品的**规则**，不是发生过的事。详情接口给出的原始值是「会」/「不会」：

| 行 | 原文 | 意思是 |
|---|---|---|
| 提前结束 | `other.earlyTermination` | 卖家**可以**在原定结束前直接结束、卖给别人。等于你有被截胡的风险 |
| 自动延长 | `goodsInfo.autoExtend` | 结束前五分钟内有人抬价就再延五分钟，可以一直延 |

把它们当**事件**来报警是错的——实测 41 条详情里 37 条「提前结束 = 会」、34 条
「自动延长 = 会」，其中 17 条还在进行中。按"为真就响"会天天误报。所以它们只
在详情屏上各占一行（没拉过详情就不画，免得把"不知道"看成"不会"），而"真的结束
了""时间真的变了"各有自己的通知。

### 通知

界面里的提醒永远是本地的、免费的。右侧那条窄栏分两段：

```
通知队列 · 2 条        ← 将要发生（还来得及改变你的行为）
⏰ 结束提醒
  20:37 还有50 …
▲ 出价被超过
  20:41 甲（当前 ¥…
── 已发生 ──          ← 刚发生过（只是告知，按发生顺序排）
■ 拍卖结束
  乙（成交价 ¥1,500）
＋ 时间延后
  丙（11-16 21:06 → 23:06）
```

上面那段是"接下来会发生什么"，下面那段是"刚刚发生了什么"。**顺序有讲究**：
窄栏放不下时先砍下面那段——将要发生的还来得及让你去加价、去看一眼，已经发生
的只是通知你一声。「已发生」段每条不带时刻：都是刚发生的，先后已经由位置说明，
18 列宽下那 6 列时刻会把拍品名挤成「20:06 时间延 …」。

到点时状态行还会闪一条提示（`⏰ 结束提醒` / `▲ 出价被超过` / `◆ 事件`）。

**五类提醒，各有开关**：

| 提醒 | 默认 | 什么时候响 |
|---|---|---|
| 结束前复查点 | 6 小时 / 1 小时 / 15 分钟 | 距结束这些时刻各响一次 |
| 出价被超过 | 开 | 站内消息报的，或每轮用当前价比出来的（见上一节） |
| 拍卖结束 | 开 | 拍品结束时，**带上成交价**（拿不到价格也照响，说"没有成交价"） |
| 截止时间延后 | 开 | 截止时间被往后推。开了自动延长的拍品会额外标一句「自动延长」 |
| 截止时间提前 | 开 | 截止时间被往前挪——和延后含义相反，这条是要你赶紧出手 |

延后和提前分成两个开关，不是洁癖：一个多给时间，一个催你出手，有人只想被后者
打扰。结束是终态，同一条拍品只响一次；时间变化按"新时间"去重，延到 21:00 和又
延到 23:00 是两件事，各响一次。

延后通知里那句「自动延长」不是装饰：雅虎的自动延长规则是"结束前五分钟内当前
价格有所上涨，就再延五分钟，可以一直延下去"。会标出这句的拍品，说明它的结束
时间是被别人一路抬上去的——也就是还有人跟你抢。卖家自己改时间不会标这句。

**提醒的节奏可以配**，在「配置 → 通知」组里：

| 设置项 | 默认 | 说明 |
|---|---|---|
| 结束前复查点 | 6 小时 / 1 小时 / 15 分钟 | **在哪些点提醒你**。想在哪几个时刻被叫一声，就把哪几个点写进去 |
| 提醒窗口 | 2 小时 | 侧栏列未来多久之内的事。更远的先不显示（**到点照样会响**，只是不提前占屏） |
| 用价格判断出价被超过 | 开 | 除了站内消息，每轮还用详情的当前价和你的出价比一次（站内消息会漏发） |
| 拍卖结束提醒 | 开 | 结束时提醒一次，带成交价 |
| 截止时间延后提醒 | 开 | 截止时间被往后推时提醒 |
| 截止时间提前提醒 | 开 | 截止时间被往前挪时提醒 |

这组数是**提醒专用**的：详情现在每轮全拉，不再有"什么时候拉一次详情"这回事，
所以这里改动的只有提醒节奏。

**一组数都是逐条加、逐条删**，不用写一整行再让程序去拆。在设置屏里选中
「结束前复查点」按 `Enter` 进去，一个点一行：

```
修改：结束前复查点
距结束这些时刻各提醒一次

❯ - 6 小时
  - 3 小时
  - 1 小时
  - 15 分钟
  - 6 分钟
```

| 按键 | 作用 |
|---|---|
| `↑` `↓` | 选点 |
| `a` | 加一个点（敲数字回车；`Tab` 切分钟/小时） |
| `Enter` | 改选中的那个点（原来的数会填进输入框，改一个数不用重敲） |
| `x` / `d` | 删掉选中的点 |
| `Esc` | 输入态先退输入态，再按一次回设置屏 |

每加一个、删一个都**立刻存盘**，没有单独的"保存"键——列表页刷新也是这样，
改完就是改完了。点按远近自动排序、重复的自动合并，所以怎么加都不会乱。删到
只剩一个就删不动了（`至少要留一个点`），空列表会让刷新逻辑无从下手。

想少被打扰就把点删掉几个；只想在最后一刻响一次，就只留 `15 分钟` 一个点。

想让它**推送到界面之外**，在「配置 → 通知」组里开对应渠道（列表上按 `s` 进）。
渠道开关、地址/凭据、扫码动作、发送测试消息**全在这一组里**，不用去别处再配一半。
这些渠道可以同时开，各自独立失败互不影响；「发送测试消息」动作项会逐条报告
成败与缺什么。

#### Webhook

最通用的一种，POST 一份 JSON 到你填的地址。Bark / ntfy / 企业微信机器人 / 飞书
机器人都能用各自的 webhook 地址直接接。

| 设置项 | 默认 | 说明 |
|---|---|---|
| Webhook 推送 | 关 | 开关 |
| Webhook 地址 | 空 | 启用时必填，`http://` 或 `https://` 开头 |
| Webhook 超时 | 5 秒 | 单次推送最多等多久 |

请求体固定：

```json
{"title": "1 小时后结束", "body": "拍品名", "asin": "l1000000003", "kind": "ending"}
```

`title` 随事件变（`15 分钟后结束` / `出价被超过` / `拍卖结束` / `截止时间延后` /
`截止时间提前`），`body` 是拍品名加必要的补充（成交价、时间变化），`kind` 是
`ending` / `outbid` / `ended` / `extended` / `shortened`（发送测试消息时是 `test`）。

#### 邮件

到点时发一封普通邮件（UTF-8，base64 传输编码，中文标题客户端能正常显示）。

| 设置项 | 默认 | 说明 |
|---|---|---|
| 邮件通知 | 关 | 开关 |
| SMTP 服务器 | 空 | 如 `smtp.qq.com` / `smtp.gmail.com` |
| SMTP 端口 | 587 | **465 = 隐式 SSL**；其它端口先明文再尝试 STARTTLS（服务器不支持就退回明文，方便自建中转） |
| SMTP 用户名 | 空 | 多数服务商要填完整邮箱地址；留空表示不登录 |
| SMTP 密码 | 空 | **填「授权码」而不是登录密码**（QQ / 163 / Gmail 都是）。界面上只显示「已设置」 |
| 发件人 | 空 | 留空则用 SMTP 用户名 |
| 收件人 | 空 | 多个用逗号分隔 |
| 邮件超时 | 20 秒 | 连 SMTP 到发完最多等多久 |

> 常见坑：QQ 邮箱要先在网页端「设置 → 账户」开启 SMTP 服务并生成**授权码**，
> 用它当密码；直接用 QQ 密码会收到 `SMTPAuthenticationError`。

#### OneBot v11（QQ 机器人）

按 OneBot v11 标准的 HTTP API 推送，go-cqhttp / Lagrange.OneBot / NapCat 等
实现都能用。

| 设置项 | 默认 | 说明 |
|---|---|---|
| OneBot 推送 | 关 | 开关 |
| OneBot 地址 | 空 | HTTP API 根地址，如 `http://127.0.0.1:3000` |
| OneBot 令牌 | 空 | 填了就带 `Authorization: Bearer <token>`，界面上只显示「已设置」 |
| OneBot 目标 | 空 | `private:QQ号` 或 `group:群号`；只写数字按私聊 |
| OneBot 超时 | 5 秒 | 调接口最多等多久 |

私聊打 `send_private_msg`（`user_id`），群聊打 `send_group_msg`（`group_id`），
消息体是 `{"message": "标题\n正文", "auto_escape": true}`。

#### 扫码挂载（微信个人号）

微信个人号没有开放平台，能接的是腾讯自己那条 **iLink（微信 ClawBot）** 通道：
用手机微信扫一张码，换一个 `bot_token`，之后就能收发消息。所以这个程序把二维码
直接画在终端里：

1. 「配置 → 通知」组里把 **微信机器人** 打开，地址默认就是官方接入点；
2. 同一组里、就在「微信登录凭据」下面会多出一行 **扫描微信机器人二维码**，
   按 `Enter` 屏幕上出二维码，手机微信扫一下并在手机上确认；
3. 屏上状态从「等待扫码」→「已扫码，等确认」→「已挂载（bot 号）」，凭据自动存进
   设置里的「微信登录凭据」，下次启动直接复用。

| 设置项 | 默认 | 说明 |
|---|---|---|
| 微信机器人 | 关 | 打开后才出现「扫描微信机器人二维码」那一行 |
| 微信登录凭据 | 空 | 扫码成功后自动填；换机器才需要手动搬 |
| 微信接入点 | `https://ilinkai.weixin.qq.com` | 登录成功后服务端给的地址优先 |
| 微信接口超时 | 15 秒 | 收消息的长轮询另按 45 秒算 |

二维码用半块字符画（一个字符格表示上下两个模块），颜色写死「白底黑块」，浅色/
深色主题都能扫。一般占 37 列 × 19 行；窗口太窄或太矮会直接告诉你"需要多少列/行"，
**不会画半个二维码让你扫不上**。过期了按 `r` 重取。

> **要能收到主动提醒，得先给它发一条消息。** 协议要求每条出站消息都带
> `context_token`，而这个 token 只从入站消息里来。所以挂载完先随便发个「你好」，
> 之后拍品提醒才能推到那个会话。程序在后台长轮询收消息、把 token 存进数据库，
> 重启也不丢。
>
> **单端绑定**：同一个微信在别处重新扫码会让旧 token 失效，届时本机会提示会话过期，
> 重新进「配置 → 通知」按一次 `Enter` 挂一次即可。

#### 扫码挂载（QQ 官方机器人）

QQ 官方机器人同样支持扫码绑定。这个程序把官方那个「扫码选机器人」的流程搬进了终端：
「配置 → 通知」组里把 **QQ 机器人** 打开 → 就在 AppSecret 下面多了
**扫描 QQ 机器人二维码**，按 `Enter`
→ 手机 QQ 扫码、**在你名下的机器人里选一个** → 程序自动取回 AppID 与 AppSecret
存进设置。

**也可以不扫码**：AppID / AppSecret 本来就是普通设置项，从 QQ 开放平台后台抄过来
手填即可。已经有凭据时再进挂载页只会显示「已挂载 888888888」，不会强行换码；
想换账号才按 `r`。

| 设置项 | 默认 | 说明 |
|---|---|---|
| QQ 机器人 | 关 | 打开后才有扫码 / 状态那一行 |
| QQ 机器人 AppID | 空 | 扫码成功后自动填 |
| QQ 机器人 AppSecret | 空 | 扫码成功后自动填，界面上只显示「已设置」 |
| QQ 绑定服务域名 | `q.qq.com` | 官方另有测试域名 `test.q.qq.com` |
| QQ 接口地址 | `https://api.bot.qq.com` | 换 token / 取网关 / 发消息的基座；本地联调可指向假服务 |
| QQ 接口超时 | 10 秒 | 调绑定接口最多等多久 |

两个渠道都打开时，两个扫码行各自独立——点哪行扫哪个渠道的码，互不顶替。
（以前只有一个「扫码挂载机器人」，两个都开时静默优先 QQ，用户根本不知道自己要扫的是哪个。）

> **AppSecret 在协议里是加密回来的**：服务端用取码时生成的一次性密钥做 AES-256-GCM
> 加密，程序解出明文后才存库。密钥只留在内存、用完即丢，不落盘也不进二维码。

**扫码只解决了「拿到凭据」，要能收提醒还得让机器人连上**

QQ 官方机器人不是「有个 webhook 地址就能推」的模型：主动消息必须知道对方的
`openid`，而这个 id 只出现在**用户先给机器人说话**的那条事件里。所以程序在后台
维持一条 WebSocket 长连（wss 地址由下面的 `/gateway` 下发，不写死）：

1. 拿 AppID / AppSecret 换 `access_token`（缓存到过期前 60 秒）；
2. `GET /gateway` 取 wss 地址，连上后 `Identify`，只订阅群聊与单聊事件；
3. 收到 `C2C_MESSAGE_CREATE` / `GROUP_AT_MESSAGE_CREATE` 就把对方 `openid` 记进
   本地库（表 `qq_sessions`），以后重启也还能推；
4. 有提醒时 `POST /v2/users/{openid}/messages`（群是 `/v2/groups/{group_openid}/messages`）
   发一条纯文本。

**所以第一次用要做一件事**：在手机 QQ 里找到这个机器人，随便发一句话。发过之后
QQ 就能正常收到推送了（有没有连上，看「配置 → 通知」里那行状态）。

> 发不出去时最常见的原因是用户在 QQ 客户端里关掉了「允许主动发送」，这时候
> 接口会回 `40034105`／`40054013`；被动回复（回复用户刚发的那条）不受这个限制。

#### 共同行为

推送走后台线程，**不会卡住界面**；任何一个渠道失败都只记一条日志，不影响采集和
其它渠道。再加新渠道：写一个实现 `Notifier.notify()` 的类 → 在 `build_notifier()`
里按配置加上它 → 在 `ChannelsConfig` 加开关，采集循环与界面都不用改。

### 防风控

- 请求之间、自动刷新的间隔都乘同一个 ±20% 抖动（设置项「节奏抖动」）；
- 自动刷新的间隔**每轮重新抽一次**，不做"每 15 分钟准点敲一次"的固定节奏。

> 2026-11-12：以前「队列任务间隔 / 队列间隔抖动 / 刷新间隔抖动」是三个配置项，
> 默认值还都是 0.2，改一个不生效。现在合并成一个「节奏抖动」，相邻请求的
> 间隔由「请求最小间隔」在 HTTP 层统一控制。2026-11-13 又整套删掉了任务队列，
> 后台动作直接起任务，不再有"任务之间"这一层等待。

**调参建议**（想更保守就调这几个）：

| 设置项 | 默认 | 说明 |
|---|---|---|
| `refresh.auto_seconds` | 180 秒 | 调大到 5–10 分钟（填 `5` + 单位「分钟」）能明显降请求量。每轮都要全拉详情，这个间隔就是请求量的主要来源 |
| `fetch.min_request_interval` | 0.5 秒 | 调到 1–2 秒更稳（也可填 `1500` + 单位「毫秒」）；调小容易被风控拦 |
| `fetch.jitter_ratio` | 20% | 请求与自动刷新的节奏抖动；调成 `0` 就是固定节奏（不建议） |
| `detail.enable` | 开 | 关掉就完全不拉详情——价格、结束时间、结束判定会一起停摆，只在排查问题时才关 |

> 全拉详情的代价要认清：每轮是"关注数"次请求。关注 50 个拍品、每 3 分钟一轮，
> 一天约 2.4 万次。想压请求量就调大刷新间隔，这是现在唯一的旋钮。

### 没有任务队列

刷新、补详情、翻译这些后台动作**直接起协程**，不排队、不串行、不去重，也没有
「任务页」可看。2026-11-13 把 `TaskQueue` 与 `UserActionRunner` 两层执行器整套
删掉了，连带删掉 `queue.enable` 这个开关（老库里的残留键启动时会自动清掉）。

为什么可以这么简单：

- **刷新互斥**由 `refresher.refresh()` 自己的 busy 守卫兜住——第二次刷新直接返回
  `正在采集中`，不会有两个任务各拿一份旧快照回写、后写的盖掉先写的（丢价格、
  丢结束时间）。TUI 在 `r` 上再做一道显式提示「已在刷新中，等这一轮结束再按 r」；
- **翻译 / 补详情**写的是内存或各自的表，不与快照整份覆盖冲突；
- **真正的请求节流**在 HTTP 层由 `fetch.min_request_interval` 控制，队列再等 2 秒
  是重复计时；
- 后台任务都收进 `Tui._tasks` 集合，退出时统一 cancel。

所以 `r` / `t` / 短信登录按下就跑，界面立刻有回应；定时刷新与手动 `r` 走的是
同一条路——每轮都把关注中的详情全拉一遍，没有"只补该补的"这回事了。

参考：挖煤姬自己的网页进详情页只拉**一次**数据，之后价格就冻结了，只在倒计时
归零、或剩余时间正好到 4:00 / 2:00 且开启自动延长时才刷新整页——也就是说
官方自己也不做高频轮询。我们的节奏比它密，所以上面几个封顶值别调大。

## 设置项：数字可以带单位

设置里凡是**时间**或**数量**，按 `s` 进去改的时候都能选单位：

```
修改：自动刷新间隔
当前值  3 分钟
新值    10
单位    秒  分钟  小时  天      Tab 切换
```

- **`Tab` / `Shift+Tab` 换单位**，输入的数字按当前单位解释：选「小时」填 `2`
  就是 2 小时（存进库里的仍是 180 → 7200 秒，配置格式不变）；
- 单位默认取「屏幕上显示的那个」，所以你看到的和输入的是同一个单位；
- 除不尽不会糊弄你：往「数据过期提醒」里填 `90 秒` 会报错说
  `不变整数分钟`，而不是四舍五入；
- 计数类项也有单位（`10 页` / `30 条` / `1 次` / `8 个`），但它们只有一个单位，
  按 `Tab` 不会变；
- 抖动比例可以按 `%` 填：`50%` 存成 `0.5`；
- 值为 0 的项会直接写明含义：`关闭` / `不限` / `不查证` / `不重试`。

| 设置项 | 默认 | 可选单位 |
|---|---|---|
| `refresh.auto_seconds` | 180 秒（显示 3 分钟） | 秒 / 分钟 / 小时 / 天 |
| `fetch.jitter_ratio` | 0.2（显示 20%） | 倍 / % |
| `storage.data_stale_minutes` | 30 分钟 | 秒 / 分钟 / 小时 |
| `notify.points_minutes` | 6 小时 / 1 小时 / 15 分钟（竖排） | 分钟 / 小时 |
| `notify.window_minutes` | 120 分钟（显示 2 小时） | 分钟 / 小时 |
| `fetch.min_request_interval` | 0.5 秒（显示 500 毫秒） | 秒 / 毫秒 |
| `fetch.timeout_seconds` | 20 秒 | 秒 / 分钟 |
| `storage.observations_retention_days` | 90 天 | 天 / 小时 |
| `login.wait_seconds` | 180 秒（显示 3 分钟） | 秒 / 分钟 |
| `channels.webhook_timeout_seconds` | 5 秒 | 秒 |
| `channels.email_timeout_seconds` / `onebot_timeout_seconds` | 20 / 5 秒 | 秒 |
| `channels.wechat_timeout_seconds` / `qq_timeout_seconds` | 15 / 10 秒 | 秒 |

## 设置项：登录

登录在「配置 → 登录」这一项里（列表页不挂快捷键）：按 `s` 进配置，`Tab` 切到
「登录」组，选中「登录挖煤姬」按 `Enter`，再按 `1` 浏览器登录 / `2` 手机验证码 /
`3` 手动粘贴。已登录时这一项叫「更换账号」。
下面几项只影响**浏览器登录**；手机验证码与手动粘贴不需要额外配置。

在 TUI 里按 `s` 可以改，改完立即生效并写库。

| 设置项 | 默认值 | 说明 |
|---|---|---|
| `login.url` | `https://www.meruki.cn/` | 拉起浏览器时打开的地址。必须是 `http`/`https` 开头的完整地址。 |
| `login.debug_port` | `9222` | Chrome 远程调试端口，用于自动捕获 Cookie（范围 `1..65535`）。 |
| `login.wait_seconds` | `180` | 等待用户在浏览器里完成登录的秒数（范围 `0..3600`；`0` = 只尝试一次）。 |

> 曾经有个 `login.fallback_to_paste`（"捕获失败就自动回退到粘贴"），实际从没被读过：
> 登录方式由你在界面上选，程序不会替你换一种。这个键已退役，老库里残留的会在启动时删掉。

### 浏览器登录是怎么工作的

程序会**自己**启动一个可调试的 Chrome 窗口，不需要你手动敲命令：

1. 用一个**独立的配置目录**（`data/chrome-profile`）启动 Chrome，并带上
   `--remote-debugging-port`。独立目录是新版 Chrome 开启远程调试的硬性要求。
2. 在这个窗口里打开 `login.url`，你正常登录即可。
3. 登录完成后程序通过 DevTools 协议自动读取 Cookie，**不需要复制粘贴**，
   也不会让你回来按任何键。
4. 配置目录是持久化的：**下次登录同一份配置仍带着登录态，会被直接复用**，
   启动后约 1 秒内就能拿到 Cookie。

| 情况 | 行为 |
|---|---|
| 登录完成后 | 自动捕获，立刻继续 |
| 浏览器里本来就登录着 | 启动后立即捕获，不用等 |
| 只安装了 Firefox / Safari | 无法走 CDP，自动回退到手动粘贴 |
| 端口被占用 / 其它程序 | 明确报出 HTTP 状态与排查命令，不会假装"端口没开" |

> 注意：Chrome 的**会话 Cookie**（无过期时间）在浏览器完全退出后不会保留，
> 这种情况下下次运行需要重新登录一次；但只要那个 Chrome 窗口还开着，
> 再次运行 `mt` 就能直接复用。

配置值非法（时区写错、端口越界、URL 缺 scheme 等）会在启动时被拦下并给出**完整字段路径**（如 `login.debug_port`）与修改建议，不会带着错误配置跑进 TUI。

## 结构

分两层：`core` 与界面无关，`tui` 只有界面。这条线有测试盯着
（`tests/test_architecture.py`）——core 不许 import tui，也不许 import rich。

```
src/meruki_tracker/
  __main__.py            # 入口：读配置 -> 装配 -> 交给 Tui
  core/                  # 换界面不用动这一层
    domain/              # 纯函数，零 I/O
      models.py          # EndTime / AuctionState / 二维状态
      lifecycle.py       # advance()：列表观测 -> 状态迁移
      detail.py          # apply_detail()：详情结果 -> 状态迁移
      render.py          # 状态 -> 展示字符串（红线在这里，但不碰 rich）
    app/                 # 用例编排：context / refresher / notices / 登录
    adapters/            # I/O：meruki 接口、浏览器、SQLite
    config.py config_options.py deadline.py errors.py jitter.py logging_setup.py net.py
  tui/                   # 只有这里碰 rich 与 prompt_toolkit
    tui.py               # 单应用 + 屏幕状态机（列表/详情/登录/设置）
    screens/             # 各屏幕的纯渲染函数，按渲染函数族拆成八个子模块（外加 re-export 的 __init__）
      __init__.py        # re-export 全部公开名（tui.py 的 `screens.xxx` 用法不变）
      common.py          # 公共小工具：脱敏、价格格式化、面板/行裁剪
      list.py            # 列表屏、视图栏、页脚、刷新遮罩
      detail.py          # 详情屏、纯文本详情、清理确认
      noticebar.py       # 右侧通知队列侧栏（将要发生的 + 刚发生的）
      login.py           # 登录各屏（方式/粘贴/Cookie 确认/等待/短信）
      qr.py              # 二维码终端渲染
      settings.py        # 设置屏与设置编辑屏
      zonetab.py         # 配置分组条（tab_bar）
    views.py             # 视图分组（关注中/已结束/无法确认/全部）
    zones.py             # 配置分组的循环切换 next_group()
```

## 三条不可动摇的原则

1. **PENDING 绝不显示倒计时**（`tests/test_render.py` 的红线测试）
2. **状态是二维的**（用户操作态 × 拍卖结果），取关判定必须基于完整观测
3. **只有 TUI 入口**（单个常驻 prompt_toolkit 应用 + rich 渲染，屏幕状态机切换），无命令行子命令
